# 김해 김씨 문중 명부 프로그램 설계 문서

- 작성일: 2026-09-21
- 상태: 승인됨 (구현 계획 대기)

## 1. 배경 및 목표

김해 김씨 집안 문중 명부(족보)를 웹 프로그램으로 만든다. 세대(몇 대손)를 기준으로 인물을 정리하고, 같은 세대끼리 가로로 한 줄에 나란히 배치되는 트리(가계도) 형태의 뷰로 한눈에 볼 수 있게 한다. 규모는 시조부터 현재까지 10대 내외, 수십~수백 명 수준이다.

주요 사용자는 고령의 가족 구성원을 포함한 문중 전체다. 별도 관리자(작성자 본인)가 데이터 정확성을 최종 승인한다.

## 2. 전체 아키텍처

- **Next.js (App Router) + Vercel 무료 티어**로 배포한다.
- 별도의 데이터베이스는 두지 않는다. 가족 데이터는 이 git 저장소 안의 JSON 파일로 저장한다.
- 데이터 파일이 git에 커밋되면 Vercel이 자동으로 재배포하므로, "git에 반영 = 사이트에 반영"이 자연스럽게 이어진다.
- 서버 쪽 API(Next.js Route Handler)가 GitHub REST API(Octokit)를 통해 커밋을 수행한다. GitHub 개인 액세스 토큰은 Vercel 환경변수로 등록하며 저장소 코드에는 노출하지 않는다.
- 세션은 서명된 httpOnly 쿠키(JWT)로 처리한다. 별도 세션 저장소가 필요 없는 무상태(stateless) 구조다.

## 3. 데이터 모델

`data/members.json`에 인물 배열을 저장한다. 각 레코드:

**필수 필드**
- `id`: 고유 식별자
- `name`: 이름
- `generation`: 세대(몇 대손)
- `parentId`: 부모(아버지) ID — 부모 미연결 상태면 `null` 가능

**선택 필드**
- `birthDate`: 생년월일
- `hanjaName`: 한자 이름
- `phone`: 연락처
- `address`: 거주지
- `deathDate`: 기일 (있는 경우에만)
- `role`: `"admin"` 등 — 관리자 승인 화면 접근 권한 판별용
- `spouse`: 배우자 정보 객체
  - `name`: 배우자 이름 (이 값이 있어야 아래 하위 항목이 의미를 가짐)
  - `birthDate`: 배우자 생년월일
  - `clanName`: 배우자 성씨/본관 (예: "김해김씨", "전주이씨")
  - `phone`: 배우자 연락처
  - `deathDate`: 배우자 기일 (있는 경우)

부모(`parentId`)는 부계(父系) 혈통만 연결한다. 배우자는 전통 족보 관례대로 남편 레코드에 속한 정보로 취급하고, 배우자 본인의 자녀 링크는 만들지 않는다(자녀는 남편 쪽 `parentId`로 연결).

`parentId`가 `null`인 레코드가 여러 개 존재할 수 있다(아직 연결되지 않은 여러 갈래). 즉 데이터 구조는 완전한 트리가 아니라 **포리스트(forest)**를 허용한다.

## 4. 로그인 (가족 열람용)

- 비밀번호 없이 **세대 + 이름 + 연락처** 3개 입력값을 `members.json`의 레코드와 대조해 본인 확인한다.
- 일치하면 서명된 httpOnly 쿠키(JWT)를 발급한다.
- 해당 레코드의 `role`이 `"admin"`이면 관리자 승인 화면 접근 권한도 함께 부여된다. 별도의 관리자 계정 시스템은 두지 않는다.
- **연락처(`phone`)는 데이터 모델에서는 선택 필드이지만, 로그인 대상이 되려면 실질적으로 필수다.** `phone`이 비어 있는 레코드는 로그인 대조 대상에서 제외한다(빈 입력값과 빈 필드가 서로 일치하는 것으로 처리하지 않음). 자가 등록(회원가입 신청) 폼과 자녀 등록 폼에는 "로그인하려면 연락처가 필요합니다"라는 안내를 표시한다.
- 항렬자 특성상 같은 세대에 동명이인이 있을 수 있다. 이 경우 실질적인 구분자는 연락처이므로, 위 규칙과 함께 이 전제를 명시해둔다.
- 대조 전에 연락처 문자열을 정규화한다(하이픈·공백 제거 후 숫자만 비교) — 입력 형식(010-1234-5678 vs 01012345678) 차이로 로그인이 실패하는 것을 방지한다.
- **초기 관리자 부트스트랩**: 최초 배포 시 `data/members.json`에 작성자 본인의 레코드를 `role: "admin"`으로 직접 커밋해 시드 데이터를 넣는다. 이후 추가 관리자가 필요하면 관리자가 "회원관리" 화면(6-1)에서 다른 레코드의 `role`을 직접 수정한다.

## 5. 등록/수정 화면

두 가지 등록 방식을 제공한다.

1. **자녀로 추가**: 트리(또는 이름 검색)에서 아버지가 될 사람을 선택하면, 세대는 부모 세대+1로 자동 계산되어 표시된다. 이름(필수), 생년월일·한자이름·연락처·거주지·기일(선택)을 입력한다. 배우자 이름을 입력하면 배우자 생년월일/성씨(본관)/연락처/기일 입력란이 추가로 열린다.
2. **새 인물 추가(독립 등록)**: 부모 연결 없이 세대 번호를 직접 입력해서 등록한다. 시조부터 순서대로가 아니라 중간 세대부터 먼저 기록해야 하는 경우에 사용한다. 이렇게 등록된 인물은 부모 미연결 상태로 남으며, 이후 실제 부모 레코드가 추가되면 기존 인물을 수정해 `parentId`를 나중에 연결할 수 있다(부모 필드도 수정 가능 항목). 배우자 입력란은 "자녀로 추가"와 동일하게 제공된다.

두 방식 모두 등록 폼에는 `role` 입력란을 두지 않는다. 서버는 pending 요청에 `role` 필드가 포함되어 있어도 무시하고 저장하지 않는다(일반 사용자가 스스로 관리자 권한을 요청하는 것을 막기 위함). `role` 변경은 관리자만 "회원관리"(6-1)에서 직접 할 수 있다.

### 5-1. 회원가입 신청 (로그인 없이 접근)

로그인은 세대+이름+연락처가 `members.json`의 기존 레코드와 일치하는지 확인하는 방식이므로, 아직 데이터에 없는 사람은 로그인도 등록 요청도 할 수 없는 공백이 생긴다. 이를 막기 위해 **"새 인물 추가" 폼을 로그인 없이도 접근 가능한 공개 URL로 별도 노출**한다("회원가입 신청" 진입점). 별도의 초대코드 등 추가 보호장치는 두지 않는다(소규모 가족 대상이라 스팸 위험은 낮고, 승인 전에는 실제 데이터에 반영되지 않으므로 관리자가 걸러낼 수 있음).

이 신청도 다른 등록/수정 요청과 동일하게 `data/pending/`에 쌓여 관리자 승인을 거쳐야 실제 데이터에 반영된다. 즉 별도의 "가입 승인" 로직을 새로 만들 필요 없이, 기존 등록 요청 승인 흐름(6장)을 그대로 재사용한다.

한 세션에서 여러 건(신규/수정)을 계속 추가할 수 있고, 화면 한쪽에 **이번 세션의 변경사항 목록(초안)** 이 쌓인다. 방금 추가한 인물을 다시 "아버지"로 선택해 이어서 등록하는 것도 가능하다.

**"최종 저장 및 승인 요청"** 버튼을 누르면, 이번 세션의 모든 변경사항이 하나의 승인 요청 묶음으로 서버에 전달된다. 서버는 이 묶음을 `data/pending/<요청ID>.json`으로 GitHub API를 통해 커밋한다(각 항목은 묶음 내부 참조를 위한 임시 ID를 가진다).

## 6. 관리자 승인 화면

- 대기 중인 승인 요청 묶음 목록을 보여준다.
- 묶음을 열면, 그 안의 신규/수정 인물들을 **기존 데이터 위에 얹은 미리보기 트리**로 보여준다. 대기 항목은 색/테두리로 구분 표시한다.
- 각 항목에 개별 승인/거절 버튼이 있다. 부모가 **이미 `members.json`에 존재하는 기존 인물**이면 자식 항목은 바로 승인할 수 있다. 반면 부모가 **같은 묶음 안에서 아직 승인되지 않은 대기 항목**이면, 그 자식 항목의 승인 버튼은 비활성화된다 — 부모가 먼저 실제 데이터에 커밋되어 정식 ID를 가져야 자식이 그 ID를 참조할 수 있기 때문이다. 이 규칙에 따라 같은 묶음 내에서는 자연스럽게 윗대손부터 순서대로만 승인하게 된다.
- 상단에 **"전체 승인"** 버튼도 제공해 한 번에 처리할 수 있다.
- 부모 항목이 거절되면, 그 부모를 참조하는 대기 중인 자식 항목들도 함께 자동 거절된다(고아 데이터 방지).
- 개별 승인 시 승인된 항목은 즉시 GitHub API로 `data/members.json`에 커밋되고 해당 pending 파일에서 제거된다. 나머지 항목은 계속 pending 상태로 남는다(부분 승인 가능). 묶음의 모든 항목이 처리되면 pending 파일 자체를 삭제한다.

### 6-1. 회원관리 (관리자 직접 등록/수정)

관리자 화면에 "회원관리" 탭을 추가한다. 관리자는 승인 대기 절차 없이 인물을 직접 추가하거나 기존 레코드(연락처, 부모 연결, `role` 포함)를 즉시 수정할 수 있고, **잘못 등록된 레코드를 삭제**할 수도 있다. 자식이 연결된 레코드를 삭제하려는 경우, 먼저 그 자식들의 `parentId`를 다른 값으로 옮기거나 미연결 상태로 되돌리도록 안내한 뒤 삭제를 진행한다(고아 참조 방지). 관리자 본인의 작업이므로 별도 승인이 필요 없고, GitHub API로 바로 `data/members.json`에 커밋된다. 가족 구성원이 스스로 신청하기 어려운 경우(고령이라 폼 작성이 힘든 경우 등) 관리자가 대신 등록해주는 경로로 쓴다.

## 7. 트리 뷰 UI

- 세대(1대~10대 내외)를 각각 하나의 가로 행(row)으로 배치한다. 부모-자녀 관계는 위 세대와 아래 세대 사이를 SVG/CSS 선으로 연결한다.
- 부모가 아직 연결되지 않은 인물(포리스트의 독립 노드)은 자기 세대 행에 표시되되 위쪽 연결선 없이 나타난다.
- 배우자가 있으면 본인 카드 바로 우측에 동일한 스타일의 카드로 나란히 표시한다(부부가 한 쌍으로 보이도록).
- 같은 부모의 자녀들은 **생년월일이 있으면 그 순서대로, 없으면 등록된 순서대로** 정렬해 나열한다.
- 카드 안 표시: 필수값(이름, 세대)은 일반 글씨 크기로, 선택값(생년월일, 한자이름, 연락처, 거주지, 기일)은 작은 글씨로 표시한다.
- 규모(수십~수백 명, 10대 내외)를 고려해 가상화나 접기/펼치기 기능 없이 가벼운 커스텀 React 컴포넌트(CSS Grid + SVG)로 구현한다. 한 행이 화면보다 넓어지면 가로 스크롤을 지원한다.

## 8. 접근성/UI 원칙

주 사용자에 고령자가 포함되므로 아래 원칙을 적용한다.

- 글씨는 기본보다 크게: 이름이 가장 크게 보이도록 하고, 생년월일 등 나머지 선택 정보는 작은 글씨로 표시.
- 세대별 행마다 배경색을 은은하게 구분해 어느 대(代)인지 한눈에 알아보기 쉽게 한다.
- 버튼/터치 영역은 크게(모바일 터치 기준), 아이콘만 쓰지 않고 한글 라벨을 병기한다.
- 로그인 화면은 입력칸 3개(세대, 이름, 연락처) + 큰 버튼 하나로 최대한 단순하게 구성한다.
- 트리가 넓어질 경우 핀치줌 대신 명확한 확대/축소 버튼을 제공하고, 이름 검색 시 해당 카드로 바로 이동/하이라이트되는 기능을 둔다.

## 9. 범위 밖 (Out of Scope)

- 휴대폰 문자(SMS) 인증 — 유료 서비스라 이번 범위에서 제외. 세대+이름+연락처 대조 방식으로 대체.
- 별도 데이터베이스 — git 저장소 자체가 데이터 저장소 역할을 한다.
- 대규모(수만 명 이상) 트리를 위한 가상화/성능 최적화 — 현재 규모(10대 내외, 수백 명 이하)에서는 불필요.
